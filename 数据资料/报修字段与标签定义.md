# 报修字段与标签定义

## 1. 使用约定

- 本文件定义平台首版 V1 字段与标签，供数据库、表单、CSV 和算法接口统一使用。
- 字段名使用英文 `snake_case`，页面标签使用中文；数据库、CSV 和算法接口统一使用字段名。
- 原始报修信息、系统预测结果和客服最终确认结果分开保存，不互相覆盖。
- `是/否/未知` 必须作为三个不同取值保存。空值不能默认为“否”。
- 首版不采集真实姓名、电话等非必要个人信息；样例数据全部使用虚构内容。
- 内部代码与页面中文展示词的对应关系见 `展示词映射.md`；页面不得直接向人工展示英文代码。

## 2. 报修人提交字段

| 字段名 | 中文名称 | 数据类型 / 允许值 | 必填 | 缺失或校验处理 |
|---|---|---|---|---|
| `ticket_id` | 报修单编号 | 字符串；由系统生成，例如 `T20261118-0001` | 系统生成 | 不允许缺失或重复 |
| `equipment_type` | 设备类型 | 受控选项：`CNC` 数控机床/加工设备、`INJECTION` 注塑机、`CONVEYOR` 输送线/传送带、`AIR_COMPRESSOR` 空压机、`VFD` 电机控制箱/变频器、`OTHER` 其他设备/不清楚 | 是 | 未选择时阻止提交；用户不需要理解后台子系统 |
| `equipment_model` | 设备型号 | 字符串 | 否 | 页面提示查看设备铭牌；不清楚时可留空，系统列入补问项 |
| `equipment_code` | 设备编号 | 字符串 | 否 | 为空不阻止提交 |
| `description` | 故障现象描述 | 文本，建议 10–1000 字 | 是 | 只要求填写看得到、听得到的现象；不得要求用户判断故障根因或子系统 |
| `occurred_at` | 故障发生时间 | 日期时间 | 否 | 未知时留空；不推测发生时间 |
| `operating_state` | 发生时运行状态 | 枚举：`STARTING` 启动中、`RUNNING` 运行中、`STANDBY` 待机、`STOPPED` 停机、`UNKNOWN` 未知 | 否 | 未填按 `UNKNOWN` 处理，可触发补问 |
| `shutdown` | 设备是否停机 | 枚举：`YES` 是、`NO` 否、`UNKNOWN` 未知 | 是 | 默认值为 `UNKNOWN`，不得默认 `NO` |
| `safety_risk` | 是否存在安全风险 | 枚举：`YES` 是、`NO` 否、`UNKNOWN` 未知 | 是 | 默认值为 `UNKNOWN`；`YES` 或 `UNKNOWN` 进入人工确认判断 |
| `alarm_code_status` | 报警代码状态 | 枚举：`PRESENT` 有代码、`NONE` 无报警、`UNKNOWN` 不清楚 | 是 | 未选择时按 `UNKNOWN`，不得推断为无报警 |
| `alarm_code` | 报警代码 | 字符串；仅当状态为 `PRESENT` 时填写 | 条件必填 | `PRESENT` 时不能为空；`NONE`/`UNKNOWN` 时为空 |
| `symptom_tags` | 现象标签 | 字符串列表；从团队确认的标签表选择 | 否 | 可由客服补充；系统推断的标签不得伪装为用户输入 |
| `submitter_note` | 补充说明 | 文本 | 否 | 为空不阻止提交 |
| `attachments` | 报修附件 | JPG、PNG、WEBP 图片或 PDF | 否 | 最多 5 个，单个不超过 5 MB；仅保存文件元数据与本机运行目录中的受控文件 |
| `submitted_by` | 提交账号 | 系统读取当前登录账号 | 系统生成 | 用于“我的报修”范围控制，不在报修页面手工填写 |
| `created_at` | 创建时间 | 系统生成的日期时间，统一时区 | 系统生成 | 不允许缺失 |

### 2.1 前台与后台字段边界

- 前台只显示上述通俗设备类型，不显示 `equipment_category`、`subsystem`、PLC、IGBT 等技术字段。
- `equipment_category` 由系统根据 `equipment_type` 或设备台账映射，用于第一层知识检索；`subsystem` 由现象、报警码和设备信息推断，用于召回参考候选。
- 前台的“其他设备/不清楚”统一保存为 `OTHER`，进入人工分流和补问，不得强行归入已有设备大类。

| 前台 `equipment_type` | 后台 `equipment_category` | 特殊规则 |
|---|---|---|
| `CNC` | `CNC_MACHINING` | 若描述含控制屏、程序、通信、控制器或报警画面等线索，可额外召回 `CNC_CONTROL` 参考候选，但不得视为精确匹配 |
| `INJECTION` | `INJECTION_MOLDING` | - |
| `CONVEYOR` | `CONVEYOR` | - |
| `AIR_COMPRESSOR` | `AIR_COMPRESSOR` | - |
| `VFD` | `VARIABLE_FREQUENCY_DRIVE` | - |
| `OTHER` | 不映射 | 直接进入人工分流和补问 |

## 3. 系统分诊输出字段

| 字段名 | 中文名称 | 数据类型 / 允许值 | 生成与缺失处理 |
|---|---|---|---|
| `predicted_category` | 建议故障类别 | 受控标签代码；包含 `OTHER_UNKNOWN` | 由规则产生；无法判断时输出 `OTHER_UNKNOWN` |
| `priority` | 建议优先级 | `NORMAL` 普通、`HIGH` 优先、`URGENT` 紧急 | `safety_risk=YES` 或 `shutdown=YES` 为 `URGENT`；安全风险为 `UNKNOWN`、`shutdown=UNKNOWN` 或关键信息缺失为 `HIGH` 并建议人工；只有安全风险 `NO`、`shutdown=NO` 且无其他升级条件时为 `NORMAL` |
| `evidence_codes` | 判断依据 | 字符串列表 | 保存实际命中的规则与知识依据；没有依据时为空并触发复核 |
| `missing_fields` | 缺失字段 | 字段名列表 | 按必需信息清单计算；无缺失时为空列表 |
| `follow_up_questions` | 建议补问问题 | 字符串列表 | 针对缺失信息生成具体问题；无须补问时为空列表 |
| `knowledge_ids` | 推荐知识条目编号 | 字符串列表 | 仅返回知识库中真实存在的条目；无匹配时为空列表 |
| `recommend_human` | 是否建议售后处理 | 布尔值 | 安全风险为“是/未知”、设备停机、停机状态未知、未知故障、关键信息不足或无适用知识时设为 `true` |
| `handoff_reasons` | 处理原因 | 字符串列表 | `recommend_human=true` 时逐项写明触发原因；否则为空列表 |
| `model_version` | 分诊规则版本 | 字符串 | 记录当前规则版本；仅供后台追溯，不在业务页面展示 |
| `triaged_at` | 分诊时间 | 系统生成的日期时间 | 不允许缺失 |

## 4. 客服确认与处理记录字段

| 字段名 | 中文名称 | 数据类型 / 允许值 | 用途与校验 |
|---|---|---|---|
| `confirmed_category` | 售后确认类别 | 与故障标签表相同的标签代码 | 售后确认或修正后的类别；用于处理记录追溯 |
| `confirmed_priority` | 客服确认优先级 | `NORMAL`、`HIGH`、`URGENT` | 客服确认或调整后的级别 |
| `customer_follow_up` | 客服补问内容 | 文本 | 保存客服向报修人提出的补问；报修人后续补充的结构化信息单独保存于操作留痕，不得覆盖原始报修字段 |
| `action_status` | 工单处理状态 | `NEW` 待分诊、`NEED_INFO` 待补充、`HUMAN_REVIEW` 待人工、`CONFIRMED` 已确认、`CLOSED` 已关闭 | 按操作更新；状态变化需留痕 |
| `action_type` | 客服操作类型 | `CONFIRM` 确认、`EDIT` 修改、`FOLLOW_UP` 补问、`SUPPLEMENT` 录入补充信息、`HANDOFF` 转人工、`CLOSE` 关闭 | 每次操作记录一条日志 |
| `action_note` | 操作说明 | 文本 | 修改或转人工时建议填写原因 |
| `action_at` | 操作时间 | 系统生成的日期时间 | 不允许缺失 |
| `action_by` | 操作人标识 | 虚构演示账号或内部用户编号 | 首版不记录真实个人信息 |

### 4.1 客服操作与状态流转 V1（冻结）

本节规定首版客服人工处理的状态和操作边界。平台只辅助售后客服完成信息核对、分诊确认和转交记录；不代表现场维修诊断已经完成，也不自动执行维修处置。

#### 状态定义

| 状态代码 | 中文状态 | 进入条件 | 允许的下一步 |
|---|---|---|---|
| `NEW` | 待客服处理 | 工单已完成自动分诊，且不存在必须人工升级或补充的信息 | `FOLLOW_UP`、`HANDOFF`、`CONFIRM` |
| `NEED_INFO` | 待补充信息 | 客服发起补问，或分诊发现非安全类关键信息缺失 | `FOLLOW_UP`、`SUPPLEMENT`、`HANDOFF`、`CONFIRM` |
| `HUMAN_REVIEW` | 待人工确认 | 存在安全风险、停机、风险状态未知、类别未知、参考/无知识匹配，或客服主动转人工 | `FOLLOW_UP`、`HANDOFF`、`CONFIRM` |
| `CONFIRMED` | 客服已确认 | 客服已核对并保存确认后的分诊类别与优先级，或明确记录无需修订 | `EDIT`、`HANDOFF`、`CLOSE` |
| `CLOSED` | 已关闭 | 客服已确认处理结论并记录关闭原因；仅表示客服工单已结束 | 无；如需再处理，应新建后续工单或由管理员恢复 |

#### 新工单的初始状态

工单提交后必须先完成现有规则分诊和知识匹配，再按以下顺序写入初始状态：

1. `safety_risk` 或 `shutdown` 为 `YES` 或 `UNKNOWN`，或 `recommend_human=true` 时，写入 `HUMAN_REVIEW`；
2. 不满足前项，但存在需要客服补充的字段时，写入 `NEED_INFO`；
3. 其余工单写入 `NEW`。

系统不得因 `EXACT` 匹配、规则命中或普通优先级而自动写入 `CONFIRMED` 或 `CLOSED`。

#### 客服操作规则

| 操作代码 | 中文操作 | 可从哪些状态发起 | 必填记录 | 操作后的状态 |
|---|---|---|---|---|
| `FOLLOW_UP` | 补问信息 | `NEW`、`NEED_INFO`、`HUMAN_REVIEW` | 补问内容、操作人、时间 | `NEED_INFO` |
| `SUPPLEMENT` | 录入客户补充信息 | `NEED_INFO` | 至少一项客户补充字段、操作人、时间；原始报修字段保持不变 | 根据“原始信息＋补充信息”重新分诊后写入 `NEW`、`NEED_INFO` 或 `HUMAN_REVIEW` |
| `HANDOFF` | 转人工处理 | `NEW`、`NEED_INFO`、`HUMAN_REVIEW`、`CONFIRMED` | 转人工原因、操作人、时间 | `HUMAN_REVIEW` |
| `CONFIRM` | 确认分诊 | `NEW`、`NEED_INFO`、`HUMAN_REVIEW` | 确认类别、确认优先级、操作人、时间；与系统建议不同须填写原因；人工复核或风险工单必须填写核对说明 | `CONFIRMED` |
| `EDIT` | 修订确认结果 | `CONFIRMED` | 修改前值、修改后值、修改原因、操作人、时间 | `CONFIRMED` |
| `CLOSE` | 关闭工单 | `CONFIRMED` | 关闭说明、操作人、时间 | `CLOSED` |

#### 安全与关闭限制

1. 存在安全风险、设备停机、风险/停机状态未知的工单，不能从 `NEW`、`NEED_INFO` 或 `HUMAN_REVIEW` 直接关闭；必须先由客服确认分诊，并至少保留一次 `HANDOFF` 或同等人工处理说明。
2. `REFERENCE`、`NONE`、`OTHER_UNKNOWN` 或存在未补齐关键字段的工单，不得伪装为确定维修结论；客服可转人工或确认“需要人工处理”，但确认记录必须说明原因。
3. `CLOSED` 仅表示客服工单流程关闭，不表示故障已排除、设备已恢复运行或现场风险已解除。

#### 留痕与原始结果保护

1. 原始报修字段、系统输出字段（如 `predicted_category`、`priority`、`knowledge_match_level`、`evidence_codes`）只读保存，不得被客服操作覆盖。
2. 客服确认结果仅写入 `confirmed_category`、`confirmed_priority`、`customer_follow_up` 等人工字段。客户补充的设备型号、状态、风险和报警信息写入 `SUPPLEMENT` 操作留痕，并仅作为重新分诊的合并输入，不改写原始报修字段。
3. 每次客服操作必须新增一条操作日志，至少保存 `ticket_id`、操作代码、状态前值、状态后值、修改前后字段值、操作说明、操作人和操作时间；不得只覆盖 `Ticket` 当前的 `action_*` 字段。
4. 首版使用虚构演示账号或内部编号作为 `action_by`，不记录真实姓名、电话等非必要个人信息。

## 5. 首版故障标签 V1

本标签是首轮分诊使用的**粗粒度疑似故障领域**，不是维修根因或最终诊断。标签依据应来自报修文本、设备信息、报警代码或已核验知识。仅凭设备停机、紧急度或单个现象词，不得断言故障类别。

| 标签代码 | 类别名称 | 纳入条件 | 排除与易混边界 |
|---|---|---|---|
| `ELECTRICAL_CONTROL` | 电气或控制异常 | 有供电、电气元件、控制器/控制面板或控制指令执行异常的具体信息 | 只有温度/振动现象时不足以判定；传感信号或通信链路异常，根因未明时优先归入 `SENSOR_COMMUNICATION` 或 `OTHER_UNKNOWN` |
| `MECHANICAL` | 机械或传动异常 | 有运动、结构、连接或传动部件异常信息，如卡滞、异响、振动、部件松脱 | “设备停机”本身不是机械故障证据；若异响由其他部件引起但未知，标 `OTHER_UNKNOWN` 或待人工确认 |
| `THERMAL_COOLING` | 温度或冷却异常 | 有设备过热/温度超限/温控失效/冷却能力不足的明确迹象 | 温度读数异常可能来自传感器，不应直接断定温控或冷却系统故障；未核明原因时记录温度现象并复核 |
| `SENSOR_COMMUNICATION` | 传感或通信异常 | 传感器/仪表读数异常、测量信号丢失，或设备之间通信中断 | 传感器读数异常与通信中断是不同子类型；首版合并用于粗分诊，需用现象标签区分，根因确认后再细分 |
| `OTHER_UNKNOWN` | 其他或未知 | 信息不足、无规则匹配、多个类别证据冲突，或故障不属于上述类别 | 不作为“兜底猜测”；输出该类时应说明未知/冲突原因并建议补问或人工复核 |

### 5.1 现象标签与故障类别的区分

1. `symptom_tags` 记录用户观察到的现象，可多选；`predicted_category` 只记录系统当前最可能的一个粗粒度故障领域。
2. 建议首批现象标签采用受控代码：`CANNOT_START` 无法启动、`ABNORMAL_TEMPERATURE` 温度异常、`ABNORMAL_NOISE` 异响、`VIBRATION` 振动、`JAMMING` 卡滞、`ALARM` 报警、`SENSOR_READING` 传感器读数异常、`SIGNAL_LOSS` 信号丢失、`COMMUNICATION_LOSS` 通信中断、`SHUTDOWN` 设备停机、`UNKNOWN_SYMPTOM` 现象不清。
3. 单条工单可以同时有多个 `symptom_tags`，但首版 `predicted_category` 为单标签；证据交叉或不足时输出 `OTHER_UNKNOWN`，不强行择一。
4. `predicted_category` 是算法预测，`confirmed_category` 是客服确认。未经人工确认的数据不能直接作为确定标签加入训练集。

### 5.2 标注判定步骤

1. 先从描述中提取可观察现象，填写 `symptom_tags`，不要先猜根因。
2. 查设备型号、报警代码及知识条目是否提供明确的子系统线索。
3. 只有证据支持某一故障领域且没有同等强度的冲突证据时，才标该类别。
4. 若证据只支持现象、不支持故障领域，标 `OTHER_UNKNOWN`，并写入 `evidence_codes`、`missing_fields` 或 `handoff_reasons`。
5. 若同一工单同时支持多个领域且无法确定主类别，V1 标为 `OTHER_UNKNOWN`，同时保留全部现象标签，交由客服确认。
6. 停机和安全风险用于优先级/人工升级，不单独决定故障类别；安全规则优先于一般现象分类。

### 5.3 标注示例

| 报修描述（虚构示例） | 现象标签 | V1类别 | 标注理由 |
|---|---|---|---|
| “设备运行中明显振动，传动部位有异响” | `VIBRATION`、`ABNORMAL_NOISE` | `MECHANICAL` | 描述直接指向运动/传动部件现象 |
| “机柜温度持续升高，冷却风扇不转” | `ABNORMAL_TEMPERATURE` | `THERMAL_COOLING` | 同时给出温度和冷却部件线索 |
| “温度显示异常跳变，设备是否过热不清楚” | `ABNORMAL_TEMPERATURE`、`SENSOR_READING` | `SENSOR_COMMUNICATION` 或 `OTHER_UNKNOWN` | 可能是测量信号异常；没有证据确认温控根因，应补问/人工确认 |
| “触摸屏无显示，同时设备不能启动” | `CANNOT_START` | `ELECTRICAL_CONTROL` 或 `OTHER_UNKNOWN` | 若无供电/控制证据，不能只靠“不能启动”定类 |
| “报警后停机，但不知道报警内容” | `ALARM`、`SHUTDOWN` | `OTHER_UNKNOWN` | 停机与报警现象不足以识别故障领域；应补问报警代码并按规则转人工 |
| “传感器数值正常，但控制器无法收到数据” | `COMMUNICATION_LOSS` | `SENSOR_COMMUNICATION` | 明确描述设备间信号/通信问题 |

### 5.4 分类适用边界

V1 分类适用于演示平台的通用虚构工单和流程联调。设备可靠性标准通常按设备、故障和维修数据组织；机器状态监测标准也强调监测参数和诊断流程需结合机器及应用场景。因此，本平台先用这些粗粒度标签作分诊入口，不能宣称它们是跨设备通用的完整故障本体。正式扩展类别前，应先确定设备类型，并用该类设备的说明书、报警表或获准的维修资料建立标签正例、反例和边界案例。

- ISO 14224:2016 将设备数据、故障数据和维修数据作为主要数据类别；该标准面向石油、天然气和石化行业，本项目只借鉴数据组织思路，不宣称符合该行业标准。https://www.iso.org/standard/64076.html
- ISO 17359:2018 提供机器状态监测程序的一般指导，并说明应用需关联相应的机器监测与诊断标准。https://www.iso.org/standard/71194.html
- ISO 13373-1:2002 针对机器振动状态监测，指出机器诊断也可能结合温度、压力等其他参数；本项目据此将可观察现象与疑似故障类别分开记录。https://www.iso.org/standard/21831.html

## 7. V1固定规则与版本记录

| 项目 | V1定义 |
|---|---|
| 故障类别 | `ELECTRICAL_CONTROL`、`MECHANICAL`、`THERMAL_COOLING`、`SENSOR_COMMUNICATION`、`OTHER_UNKNOWN` |
| 报警代码状态 | `PRESENT`、`NONE`、`UNKNOWN`；`PRESENT` 时必须填写代码 |
| 安全风险/停机 | `YES`、`NO`、`UNKNOWN` 三值保存；未知不等于否 |
| 紧急优先级 | 安全风险为 `YES` 或 `shutdown=YES`：`URGENT`；安全风险为 `UNKNOWN`、`shutdown=UNKNOWN` 或关键信息缺失：`HIGH` 并人工确认；只有安全风险 `NO`、`shutdown=NO` 且无其他升级条件：`NORMAL` |
| 人工升级 | 风险是/未知、设备停机/停机状态未知、未知类别、必要信息缺失、分类置信度低于 0.60 或无匹配知识时建议人工 |
| 人工确认字段 | 预测类别与确认类别、预测优先级与确认优先级分别保存，不覆盖原始值 |
| 数据范围 | V1采用虚构工单和演示知识；不据此宣称真实企业诊断效果 |
